StepsNumbered cards for sequential work.

ol.steps turns each item into a numbered card. The number is printed with two digits by a CSS counter. Each step carries a title, a short description and an optional check line: the reader knows what to look at to tell the step is done.

Classes
.steps · .check · .s-warn · .s-bad
State
aria-current="step" · data-state="done|blocked" · start
Structure
ol.steps > li > h3 + p + p.check
JS
Not needed

01

Anatomy

A step is three lines: what to do, how to do it, how to tell it is done. Only the title is required.

Example · a single step

  1. Upgrade the read replica

    Move the orders-replica instance to the new version first; the primary keeps taking writes meanwhile.

    Check: replica lag dropped below 5 seconds.

PartRole
li::beforeThe number badge; 01, 02… from the list-item list counter, so it follows start
h3Imperative, a single action
pHow to do it; stops at 72 characters
p.checkThe completion criterion; green, with a check icon

02

Variants

A step can be as short as a title or long enough to carry code and a note. The start attribute is all you need to continue numbering midway.

Example · titles only

  1. Create a branch

  2. Make the change

  3. Open a merge request

Example · a step with code and a note

  1. Dry-run the migration

    The migration tool prints the SQL before applying any changes.

    Lock

    If you see ACCESS EXCLUSIVE in the output, leave the migration for a maintenance window.

    Check: the output has only the two expected statements.

Example · continuing the numbering

  1. Send traffic to the new target

    Set the weight on the load balancer to 100 / 0.

  2. Shut down the old target

    If no errors show for an hour, delete the old target group.

The visible number comes from the browser's list counter (list-item); start="4" is enough for both screen readers and the badge. Delete the counter-reset:s 3 line that older versions needed.

03

States

A step can be current, done or blocked. The state is given through ARIA (aria-current) or data-state, and is always said in text too; color only reinforces it.

Example · done, current, blocked

  1. Take the backup (done)

    Check: the backup is in the bucket, 4.2 GB in size.

  2. Run the migration now

    Apply migration 0043 with migrate up.

    Check: stop if the table lock exceeds 30 seconds.

  3. Upgrade the read replica blocked

    Replica lag is over 5 minutes; do not start until the migration finishes.

    Stop criterion: roll back if the lag keeps growing.

StateMarkupLook
Currentaria-current="step"A 2px drawing border; screen readers say “current step”
Donedata-state="done" + textGreen number badge
Blockeddata-state="blocked" + textDashed border, red badge
Check line.check.s-warn · .check.s-badA warning or stop criterion; choose the icon yourself

data-state does not reach screen readers. Either write the state visibly (a .state label) or add it to the title as .visually-hidden text; the first step above uses the second way. If a script changes the state, update the attribute and the text together.

Example · the numbering continues, and so does the state

  1. Send traffic to the new target done

  2. Watch the error rate for an hour (current step)

  3. Shut down the old target

04

In context

Three typical jobs: a new developer getting access, responding to an incident, and shipping a release.

Example · onboarding

  1. Activate your account in the identity provider

    Use the link in the invitation email to set your password and two-step verification.

    Check: you can see the app list in the single sign-on dashboard.

  2. Request the developer role

    Choose the dev-readonly role in the access request form; your manager approves it.

    Check: aws sts get-caller-identity prints your role.

  3. Clone the repository and run the tests

    make bootstrap && make test sets up the local environment and runs the unit tests.

    Check: all tests passed.

Example · incident response

  1. Declare the incident first 5 minutes

    Open the incident channel, write down the severity, assign a coordinator.

  2. Contain the impact

    If the errors started with the last deployment, roll back first and look for the cause later.

    Check: the 5xx rate dropped below the alert threshold.

  3. Announce the status

    Post a short update every 30 minutes, even if nothing has changed.

  4. Schedule the post-incident review within 5 business days

    Look for causes, not culprits; follow-up work is recorded with its owners.

Example · release procedure

  1. Push the release tag

    git tag v1.9.0 && git push origin v1.9.0; the build sees the tag and produces the image.

    Check: web-api:1.9.0 is in the image registry.

  2. Run the smoke test on staging

    Once sync has updated staging, start the end-to-end test suite.

    Check: 42 of 42 scenarios passed.

  3. Roll out to prod gradually

    10% of traffic, 50% after 15 minutes, all of it after another 15 minutes.

    Check: p95 latency stays under 800 ms at every stage.

05

Do / don't

A good step is a single action, and you can see when it is done. If a step holds three jobs, write three steps.

Do · one action, a measurable finish

  1. Warm the cache

    Check: hit rate above 80%.

Don't · many jobs in one step

  1. Preparation

    Warm the cache, also silence the alerts and, if needed, take a backup and tell the team.

Accessibility

An ol is announced as an ordered list; a screen reader says “2 of 3”, while the visible number badge is decoration. The check icon is decoration too; start the check line with a word such as Check:. If steps need to be ticked off, use the runbook (.runbook).
